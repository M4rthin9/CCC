# Additional visitor QR attendance

## Local development preview

`npm run dev:registration-preview` starts a loopback-only API at `http://127.0.0.1:18889`. It uses the real authentication and attendance handlers against an in-memory SQLite database with the repository migrations, seeded only with synthetic reservations. Production bindings and `.dev.vars` are never loaded; notifications and OCR are disabled. State resets when the API restarts. Requires Node with `node:sqlite` (the same requirement as the attendance verification script).

In the sibling Dashboard project, start Vite with `VITE_API_BASE=http://127.0.0.1:18889` and `VITE_REGISTRATION_PREVIEW=true` in the process environment, using `npm run dev -- --host 127.0.0.1 --port 18890 --strictPort`. Open `http://127.0.0.1:18890/#/registration`; the page shows a LOCAL PREVIEW banner. Test login: `officer` / `Preview123!`.

Open `http://127.0.0.1:18889/passes` on another screen for signed test QR passes, or copy a pass's QR text into the scanner field. The fixtures include unregistered, partly registered, fully registered, pending finance confirmation, VIS and historical bookings. The late-payment fixture has a local-only button to confirm payment, after which its QR becomes available and the officer overview updates. Duplicate scans use the actual check-in safeguards. These test credentials have no access to production.

## Registration officer page

Open the dashboard's dedicated **`/#/registration`** page (also linked from the main login page). Signed-out officers see an officer-specific login form. Sign in with an existing reception (`Tadtel`) staff account to open the scanner directly, with an officer name and logout button. Superadmin, Admin and Finance accounts can also use this page. Other roles cannot open the scanner or read attendance. Administrators create individual officer accounts through the existing Users page; no shared password, new account system or role migration is needed.

The officer page runs separately from the dashboard navigation and starts on today's Bangkok date. Scan a visitor's QR, compare the reservation and payment details, and register each arriving guest. The daily list records the guest, booking reference, check-in time and officer. Choose another date to view its saved entries; scanning/check-in is available only for today, and the page rolls over to the next Bangkok day automatically. Logout returns to the officer login page and clears the visible reservation information. The regular dashboard login and existing daily reports continue as before.

The **daily table registration overview** reads current bookings and payment status directly, independently of a printed or previously sent report. It shows each booking reference (one reserved table), its main guest and party, payment status, arrival count, and **not registered / partly registered / fully registered** status. Fully registered means every expected named guest has checked in; payment confirmation alone does not mark a table as arrived. Search by reference, guest name or phone and filter VIS/TBL and registration status. Active-table summary counts exclude cancelled, rejected and refunded bookings; those bookings remain available under the inactive filter with any existing check-in evidence.

While today's page is visible, the overview refreshes approximately every 30 seconds and after each check-in; a manual refresh and last-updated time are also shown. A booking whose payment is confirmed after the daily report was sent becomes eligible in the current officer workflow and can check in later on the same booked Bangkok day. No report is regenerated, resent or changed. The page does not infer which payments were late relative to a report because no report-send timestamp is recorded. Historical daily overviews read the archive as needed, preferring the live record if a duplicate exists, and remain read-only for check-in.

## Visitor passes and attendance

The visitor home guide, booking-success screen and booking-status result include an expandable four-step registration guide in Thai, English, Chinese and Vietnamese: keep the reference, wait for approval/payment confirmation, create and save the entry card using the main holder's original ID/passport number, then bring the card and each guest's original identification to the registration desk. It explains group arrivals, late payments, rescheduling and the existing VIS phone restrictions.

The visitor entry pass is composed on the device as a 1080 × 1580 PNG with the official seal, a large unchanged signed QR, booking reference and localized visit date. Download saves the complete card; supported phones also offer native image sharing and long-press image saving. Saved images can be shown offline, while officers still check the latest booking status. The image contains no ID/passport number, visitor names or payment details. If image export fails, the original QR stays visible for scanning or a screenshot. Switching booking/language discards stale card generation and releases the previous image URL.

The officer login and check-in page use the institution's existing official seal and a scoped navy/gold design, with a cyan camera viewfinder, a Bangkok clock, daily metrics, clear allowed/blocked results and guest check-in buttons. Scanner and verification panels appear side by side on larger screens and stack on phones; full booking details and the individual audit list remain available in expandable sections. Scan animation respects reduced-motion preferences. Presentation changes do not alter payment approval, admission checks, daily reporting or stored attendance.

Visitors open their booking status after finance confirmation (`เสร็จสิ้น`), enter the main booking holder's original ID/passport number, and show or save the entry QR. Completed payment is the final admission authority: blank, pending or outdated individual approval flags do not add another QR or check-in gate. The original approval fields remain unchanged. A single booking QR lets staff register each named arriving guest separately, including guests arriving at different times. The QR is distinct from PromptPay and bank-slip QRs and contains only a signed booking reference and visit date. Visitors should bring their original identification; staff must match the displayed guest name to that document.

Staff open **ตรวจสอบเข้างาน** (`#/attendance`) in the dashboard. Superadmin, Admin, Finance and Tadtel can scan with the rear camera or paste the QR text/use a keyboard QR scanner. The camera decoder supports browsers without native BarcodeDetector, including iOS; camera access requires HTTPS or localhost and browser permission. Decoding runs on the device; camera images are not uploaded. Staff see the current payment status, booked date, individual approvals and previous entry times. Named guests on a finance-confirmed live booking may check in, on their booked Bangkok date. `ชำระแล้ว` alone means pending finance review and does not grant entry. Finance confirmation is sufficient; no repeated individual approval is required for QR issuance or attendance.

Each check-in saves the guest name, UTC timestamp and authenticated operator in `visitor_attendance`, uniquely keyed by booking reference, visit date and guest identity hash. The list below the scanner shows entries for the selected date in Bangkok time. Duplicate and simultaneous scans return the original attendance record. A conditional database insert rechecks payment, date and roster, so a cancellation, refund or roster edit during scanning cannot grant a new entry. Refund history also blocks re-admission if a booking status was later changed manually. Entry QRs expire at midnight after the booked Bangkok date; rescheduling requires a new QR. Archived reservations cannot check in.

Attendance is additional. It never updates reservation status, visitor counts, prices, payment evidence, or existing daily/monthly reports. No existing report query or print/export path changes.

After scanning, staff see the full reservation summary and every guest's details directly on the scanner screen. For TBL bookings, compare the reference, visit date, names/ID or passport numbers, recorded visitor count and status with the existing **ทะเบียนจัดการโต๊ะ (TBL)** daily report before pressing each guest's check-in button. Contact information, booking amount, age counts, booking dates/source, individual relationships, ages, religions and food restrictions are also shown. Named, checked-in and not-yet-arrived counts remain separate from the original reservation count. These details are returned only to authorized staff; the visitor QR remains a signed reference/date, and attendance records never store ID numbers or dietary information. Slip storage keys and verification internals are excluded from the scan response.

Dispatcher POST actions:

| Action              | Access                                                                      | Parameters                                                                                                                     |
| ------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `getVisitorEntryQr` | Public, identity verified; 20 attempts per IP per 5 minutes, including bulk | `ref`, `visitorId`                                                                                                             |
| `checkVisitorEntry` | `visitor_approval` or `confirm_payment` permission                          | `qr`                                                                                                                           |
| `checkInVisitor`    | Same staff permission                                                       | `qr`, `guestKey` returned by the entry check                                                                                   |
| `getAttendance`     | Same staff permission                                                       | `date` (`YYYY-MM-DD`, defaults to today in Bangkok); returns individual `rows`, current daily `tables` and `asOf` refresh time |

Apply migration `0029_visitor_attendance.sql` to the target D1 environment, deploy the backend, then deploy the dashboard and visitor frontend. No new secret or role permission is needed. Existing JWT signing configuration signs the audience-restricted entry passes; entry passes cannot authenticate as staff.

Verification: `npx tsx scripts/verify-attendance.ts`, backend typecheck/lint/build, dashboard check/test/lint/build, frontend check/lint/build. The attendance script uses an in-memory database with the real migrations and exercises QR encoding/decoding, identity and authenticated-role restrictions, payment review, individual approval, date/expiry, duplicate and racing scans, roster changes, cancellations/refunds, rate limiting, and unchanged reservation/report fields.
